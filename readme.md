# deBridge Orders QA

TypeScript CLI для проверки заказов: получить выборку по кошельку → пройти страницы по 25 → отдельно загрузить детали каждого заказа → проверить наличие адреса → сохранить отчёт.

Адрес ищется во всех строковых значениях JSON, включая вложенные объекты и массивы. Сравнение точное, с сохранением регистра. Отчёт содержит все пути совпадений, например `$.receiverDst.stringValue`.

## Запуск

Нужны Node.js 22+ и npm. Команды выполняются из корня репозитория:

```bash
npm install
npm start
```

Программа сама вызывает реальный API. По умолчанию проверяет все страницы кошелька `BUnGokFzA1wu8vb6adHfyhnNvCxaVt6QyPNmmUNWPwET` в режиме `Mixed` и сохраняет результат в `reports/orders.json`.

```bash
# Другой кошелёк: замените ADDRESS реальным адресом
npm start -- --wallet ADDRESS

# Пробный запуск на одной странице
npm start -- --max-pages 1 --output reports/first-page.json

# Справка
npm start -- --help

# Проверка типов и автоматические тесты без запросов к реальному API
npm run check
npm test
```

Прогресс страницы и результат каждого заказа выводятся сразу по мере обработки. `PASS` — проверка прошла, `FAIL` — полученные детали не прошли проверку, `ERROR` — ошибка получения или выполнения проверки. В итогах эти категории считаются отдельно. Ошибка деталей одного заказа не останавливает проверку остальных. Запросы выполняются последовательно, с таймаутом и ограниченными повторами временных ошибок.

Код завершения `0` означает полную непустую проверку, в которой все заказы прошли проверки. Код `1` означает ошибку, провал проверки, пустую выдачу или неполный запуск. При `--max-pages 1` код `1` ожидаем, если остались другие страницы.

## Дополнительные фильтры

Фильтры передаются JSON-файлом. Например, `examples/filters.json`:

```json
{
  "giveChainIds": [42161],
  "takeChainIds": [7565164],
  "orderStates": ["Fulfilled"],
  "filterMode": "CrossChain"
}
```

```bash
npm start -- --wallet ADDRESS --filters examples/filters.json
```

| Параметр | Назначение |
|---|---|
| `giveChainIds`, `takeChainIds` | Исходные и целевые сети, массивы числовых ID API |
| `orderStates` | Статусы заказов, например `Created`, `Fulfilled`, `ClaimedUnlock` |
| `blockTimestampFrom`, `blockTimestampTo` | Период создания, Unix timestamp в секундах |
| `maker`, `creator`, `fulfiller` | Адреса участников заказа |
| `unlockAuthorities` | Адреса с полномочиями на разблокировку |
| `orderAuthorityInSourceChain`, `orderAuthorityInDestinationChain` | Адреса управления заказом |
| `referralCode` | Числовой referral code |
| `orderTradeType` | `None`, `Market` или `Limit` |
| `filterMode` | `CrossChain`, `SameChain` или `Mixed` |

Кошелёк остаётся обязательным условием поиска и проверяется в деталях. Если в JSON задан `filter`, он должен совпадать с `--wallet`. Неизвестные параметры и некорректные значения отклоняются. Дополнительные фильтры ограничивают выборку; сами по себе они не добавляют проверок полей в деталях.

## Расширение

| Задача | Что изменить |
|---|---|
| Другой кошелёк, сеть, статус или период поиска | Только параметры запуска или JSON-файл |
| Новое поддерживаемое backend поле фильтра | `OrderFilters` в `src/types.ts` и проверку конфигурации в `src/cli.ts` |
| Проверка статуса, суммы, токена или обязательных полей | Добавить `Validator` и подключить его к `runOrders` в `src/cli.ts` |
| Новый тип заказа или endpoint деталей | Маршрутизацию в `src/api.ts` и соответствующие типы |
| Другой backend | Реализовать интерфейс `OrdersApi` |
| Поиск без кошелька | Сделать wallet-фильтр и его валидатор опциональными в CLI |

Фильтры определяют, какие заказы запросить. Валидаторы проверяют полученные детали. Новый валидатор возвращает имя проверки, результат, пути совпадений и сообщение. Например, проверка статуса должна сравнивать конкретное поле `state`, а не искать строку по всему JSON.

`src/runner.ts` отвечает за пагинацию и сбор отчёта. При добавлении фильтра или валидатора его менять не требуется. Это позволяет использовать код для регрессионных API-проверок по схеме «выборка → детали → проверки → отчёт».

## API и текущая проверенность

По умолчанию используется `https://stats-api.dln.trade`; хост можно заменить через `--base-url`.

- Список: `POST /api/Orders/filteredList`, `take: 25`, `skip: 0, 25, 50…`.
- Cross-chain детали: `GET /api/Orders/{id}`, проверяется `orderId.stringValue`.
- Same-chain детали: `GET /api/SameChainSwap/{id}`, проверяется `swapId.stringValue`.

Рекурсивный валидатор кошелька применяется к обоим типам. Маршрут same-chain реализован по документации; соответствие `orderId` из списка идентификатору `swapId` ещё требует проверки на живом ответе. Запрос деталей при клике UI также пока не подтверждён сетевым захватом. Полный live-прогон из среды разработки не выполнен из-за ошибки DNS; автоматические тесты используют подготовленные ответы.

Пагинация обнаруживает повторные ID, преждевременные пустые/короткие страницы и изменение `totalCount`. При обновлении данных на сервере offset-пагинация не гарантирует стабильный снимок даже при неизменном количестве заказов. Для воспроизводимой выборки можно задавать период создания.

## Повторные попытки

Для каждой страницы списка выполняется максимум три попытки при любой ошибке запроса или проверки ответа. Между неудачными попытками пауза 10 секунд; ошибка и номер попытки выводятся в консоль. После первого успешного ответа сразу начинается проверка заказов страницы. После третьей ошибки обход прекращается, ошибка сохраняется в отчёте.

Детали каждого заказа запрашиваются один раз. Ошибка сохраняется в отчёте, проверка остальных заказов продолжается. `Retry-After` не используется: интервал повторов списка фиксирован.

Между запросами деталей выдерживается пауза 1 секунда, включая переходы между страницами и запросы после ошибок. Это снижает частоту обращений, но не гарантирует отсутствие HTTP 429.
